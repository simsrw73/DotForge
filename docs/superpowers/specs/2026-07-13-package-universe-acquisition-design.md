# Package Universe — Phase A: Catalog Acquisition — Design

**Date:** 2026-07-13
**Status:** Approved; Choco section amended 2026-07-14 (skip → `$skiptoken` paging) and substantially rewritten 2026-07-15 (date-bucketing, adaptive bisection, and incremental sync all deleted after a live run disproved the 10,000-item cap's applicability to `$skiptoken` paging — see Acquisition Strategy → Choco).

**Validated end-to-end against live data on 2026-07-16.** A full run produced **30,251 packages — scoop 5,286, winget 13,763, choco 11,202 — with an empty `pipeline_log` (zero errors, warnings, or review rows) and zero duplicate `(source, package_id)` pairs.** The choco walk took **282 requests for 282 pages (1:1 — no retries), ~27 minutes, terminating on a missing next link with `complete=True, errors=0`**, and its 11,202 rows match `community.chocolatey.org`'s own published package count exactly. Independent corroboration of the design's central claims: the walk crossed item 10,000 at page 250 and continued returning full 40-entry pages (**the 10,000-item cap provably does not apply to `$skiptoken` paging**), and its 282 pages are the same 282 that the superseded 2011 date bucket burned to return 5 rows (**filters are applied post-pagination**). Whole run: ~54 minutes.
**Part of:** a larger admin-tooling effort to build a cross-catalog package index (identity linking + metadata merge + categorization). This spec covers only the first phase, acquisition. Later phases (identity clustering, metadata merge, categorization, and optional AI-assisted categorization / additional ecosystems) are each sequenced as their own future spec.

## Problem

DotForge's `trifle` today searches scoop/winget/choco/npm/crates/psgallery/pypi on demand, one query at a time, with per-query caching. There is no artifact anywhere that says "here is every package these catalogs contain" — that's a prerequisite for the larger goal (an index linking the same real-world application across every package manager it's distributed through, with merged metadata and categories). This spec builds that prerequisite for the three catalogs that anchor the effort: scoop, winget, and choco.

## Goals

- Produce a complete, offline snapshot of every package in scoop (locally-added buckets), winget, and choco, with whatever metadata (name, version, description, homepage, license, publisher, tags) each catalog can supply cheaply. All three are full rebuilds every run; choco's earlier "initial full crawl plus ongoing incremental refresh" model was removed on 2026-07-15 once live testing proved a complete choco walk costs only ~281 requests (~21 minutes) — see Acquisition Strategy → Choco.
- Store the result in a form later phases (identity clustering, metadata merge, categorization) can query and build on directly.
- Never let one catalog's failure (rate-limited API, unreachable download, corrupt file) block the other two, or abort a partial run.
- Log anything ambiguous or broken for later human review, without treating it as fatal.

## Non-Goals

- Cross-catalog identity linking, metadata merging, or categorization — later phases, each with their own spec.
- npm/crates/pypi/psgallery/gem/nuget/vcpkg/pip/cpan/luarocks acquisition — those are cross-reference targets for a later phase (search-and-validate against the scoop/winget/choco-derived universe), not full-catalog crawls themselves.
- Every scoop bucket that exists in the world — scoop has no central registry; scope is whatever buckets are already added on the machine running the build.
- Incremental/diff-based updates for **any** of the three catalogs — all are full rebuild-from-scratch every run (scoop is free local-disk reads; winget is a full snapshot re-download regardless; choco is a ~281-request full walk). Choco was originally specced as the exception, on the assumption its API's 10,000-item cap made a full re-crawl impractical. Live testing on 2026-07-15 disproved that assumption outright — the cap does not apply to the `$skiptoken` paging this spec now uses, and an incremental `LastUpdated`-filtered query would cost *the same* ~281 requests as a complete walk (filters are applied post-pagination — see Acquisition Strategy → Choco). Incremental sync bought nothing and cost complexity, so it was removed along with the `sync_state` table and the `-Fresh` switch.
- rpm/dpkg/apt/yum/dnf/pacman/homebrew or any non-Windows ecosystem — future work, unscoped here.
- Shipping this data as part of the installed DotForge module — this is author-side admin tooling under `build/`, exactly like `Build-DFCategoryDb.ps1` / `Build-DFToolIdentities.ps1`, never loaded by the module itself.
- Mirroring via a third-party repository manager (Nexus Repository, ProGet, etc.) as an alternative data source — investigated and rejected. Both default to lazy, on-access proxy caching (they populate metadata only for packages a client actually requests through them, not the full upstream catalog). ProGet's "Feed Importer" bulk-import feature is the closest fit, but it is Inedo's own client against the same public `community.chocolatey.org` OData API — it has no privileged access to a pre-existing full catalog and would hit the identical rate limits, the identical 10,000-item cap, and the identical broken `startswith()`/`Id`-filter behavior documented below. No shortcut here.

## Pipeline Context (for later phases)

This is Phase A of a multi-phase pipeline. All phases share one SQLite working database (`universe.db`) rather than each inventing its own storage:

- **Phase A (this spec):** `raw_packages` — per-catalog raw acquisition.
- **Phase B (future):** `identity_clusters` / `cluster_members` — cross-catalog identity linking, plus search-and-validate cross-references into npm/crates/pypi/psgallery/gem.
- **Phase C (future):** `merged_metadata` — normalized, merged per-cluster metadata.
- **Phase D (future):** `categories` — derived ontology/tags.
- **Phase E/F (future, optional):** AI-assisted categorization; additional ecosystems (rpm/deb/homebrew).

Every phase writes into one shared log table, `pipeline_log`, tagged by `stage`. This is the "log for later manual review" mechanism spanning the whole pipeline, not just this phase.

## Data Model

```sql
CREATE TABLE raw_packages (
  id          INTEGER PRIMARY KEY,
  source      TEXT NOT NULL,   -- 'scoop' | 'winget' | 'choco'
  package_id  TEXT NOT NULL,   -- catalog-native id ('bucket/name' for scoop, winget PackageIdentifier, choco id)
  name        TEXT,
  version     TEXT,
  description TEXT,
  homepage    TEXT,
  license     TEXT,
  publisher   TEXT,
  tags        TEXT,            -- JSON array, serialized
  extra       TEXT,             -- JSON object, source-specific leftover fields
  fetched_at  TEXT NOT NULL,    -- ISO 8601 UTC
  UNIQUE(source, package_id)
);

CREATE TABLE pipeline_log (
  id         INTEGER PRIMARY KEY,
  stage      TEXT NOT NULL,   -- 'acquire' | 'link' | 'merge' | 'categorize'
  source     TEXT,            -- nullable: which catalog, if applicable
  package_id TEXT,            -- nullable: which package, if applicable
  level      TEXT NOT NULL,   -- 'warning' | 'error' | 'review'
  message    TEXT NOT NULL,
  logged_at  TEXT NOT NULL    -- ISO 8601 UTC
);
```

(An earlier revision defined a third table, `sync_state`, holding a `last_synced_at` watermark to drive choco's incremental refresh. It was removed on 2026-07-15 along with the incremental design — see Acquisition Strategy → Choco.)

- `level = 'error'`: something failed outright (a catalog fetch failed, a page/file was unreadable after retries).
- `level = 'warning'`: a single item was skipped (unparseable manifest, missing required field).
- `level = 'review'`: parsed fine, but worth a human glance later (e.g. no default-locale winget manifest found, a homepage URL that fails basic format validation, an empty scoop `bin` array).
- **Truncation is per-source, not a blanket table wipe.** Each run rebuilds one source at a time, so one catalog's failure never destroys another's rows. Scoop and winget do `DELETE FROM raw_packages WHERE source = 'scoop'` / `'winget'` before re-acquiring. **Choco upserts, then prunes:** it uses `INSERT ... ON CONFLICT(source, package_id) DO UPDATE` per row, then deletes any pre-existing choco row whose `package_id` did not appear in this run's walk. Upsert-then-prune rather than delete-then-insert is deliberate: a walk that fails partway leaves the previous run's data intact rather than emptying the table, and the prune step (which only runs after a *complete* walk — see Acquisition Strategy → Choco) is what detects packages removed upstream. `pipeline_log`'s truncation is unchanged: each run clears only this run's own `stage='acquire'` rows, leaving other future phases' log history untouched.

## Acquisition Strategy Per Catalog

### Scoop

Thin wrapper around the existing `Build-DFCatalogScoopIndexData` (`Private/DFCatalog.Scoop.ps1`) — it already reads every manifest from every locally-cloned bucket (name, bucket, version, description, homepage, license), entirely from local disk, no network. Map each result into `raw_packages` with `source = 'scoop'`, `package_id = "$bucket/$name"`. Scope is exactly whatever buckets are added on the machine running the build — there is no broader "every scoop bucket" universe to reach for.

### Winget

The local SQLite index (`Private/DFCatalog.Winget.ps1`'s `index.db`) has `id`/`name`/`moniker`/`latest_version` only — no description/homepage/publisher/tags by design. Rather than pay for tens of thousands of slow `winget show` CLI spawns, acquire directly from the public source of truth:

1. Download a zip snapshot of `microsoft/winget-pkgs`'s default branch (GitHub's zipball/tarball endpoint — no `git` dependency, no history, just the current tree). This mirrors the existing in-process zip-extraction approach `Get-DFCatalogWingetIndex` already uses for the msix. No incremental logic — full re-download and replace each run.
2. This is the single most expensive step in Phase A: the repo holds every published version of every package under `manifests/<letter>/<publisher>/<package>/<version>/`, so expect a sizeable download (plausibly several hundred MB+) and a non-trivial extraction/parse pass. Budget real wall-clock time for this step; it is not expected to be fast.
3. For each package, resolve only its **latest version folder** — version folder names are compared using `[version]` parsing where they parse cleanly, falling back to ordinal string comparison for the minority that don't (winget versions aren't strictly required to be semver). Within that folder, the actual manifest layout is one of two current winget-pkgs formats (confirmed against the live repo, e.g. `manifests/m/Microsoft/VisualStudioCode/<version>/`):
   - **Multi-file (the common case today):** a small version manifest `<PackageIdentifier>.yaml` (`ManifestType: version`, carrying a `DefaultLocale:` tag like `en-US`), an `<PackageIdentifier>.installer.yaml` (skipped, not needed), and one or more locale files — **every** locale file is tagged, including the default one: `<PackageIdentifier>.locale.<BCP47Tag>.yaml` (`ManifestType: defaultLocale` for the one matching `DefaultLocale`, `ManifestType: locale` for any others). There is no untagged `<PackageIdentifier>.locale.yaml` file in this format. Read the version manifest's `DefaultLocale` field, then load `<PackageIdentifier>.locale.<DefaultLocale>.yaml` for `PackageName`, `Publisher`, `ShortDescription`/`Description`, `PackageUrl`/`Homepage`, `License`, `Tags`.
   - **Singleton (an older/simpler format, still present for some packages):** a single `<PackageIdentifier>.yaml` with `ManifestType: singleton` holding installer and locale fields together — read the same fields directly from it.
   - Identify which format a version folder uses by parsing the "root" file (matches `*.yaml`, not `*.installer.yaml`, not `*.locale.*.yaml`) and checking its `ManifestType`.
4. YAML parsing uses the `powershell-yaml` module (a new build-time-only dependency — never required by the shipped DotForge module or its end users, exactly analogous to how some existing build tooling already assumes `gh` is available).
5. A package where neither the tagged default-locale file nor a singleton manifest can be resolved logs a `review` row and is skipped (some winget-pkgs entries are genuinely incomplete).
6. **Most locale fields are OPTIONAL, and reading them must use index access, not dot access.** `Tags`, `PackageUrl`, and `Description` are all routinely absent. `ConvertFrom-Yaml` returns a `Hashtable`, where `$content.Tags` on a manifest with no tags **throws** under strict mode while `$content['Tags']` returns `$null`. Measured live on 2026-07-15: this cost **4,734 of 13,763 packages (~34%)** — each one caught by the item-level isolation rule, logged as a `warning`, and skipped. The run "succeeded" and only the final row count betrayed it (9,029 instead of 13,763). Two lessons are worth more than the fix: item-level isolation converts a crash into silent partial data, so **row counts must be sanity-checked against the directory count** the enumerator reports (`found N package directories` vs. rows emitted — they should be within a hair of each other); and both existing test fixtures declared `Tags`, which is precisely why the suite stayed green.

### Choco

Reuses `ConvertFrom-DFCatalogODataEntry` (`Private/DFCatalog.Choco.ps1`) for id/name/description/version/homepage, extended to also read `Authors` → `publisher` and `Tags`/`LicenseUrl` → `tags`/`license` — see the field-mapping note below for a real gotcha in reading `Authors` correctly.

This section was substantially revised after live-testing `community.chocolatey.org`'s OData v2 API directly (2026-07-14) surfaced several undocumented or under-documented server behaviors that break the naive "just page with `$skip`/`$top`" approach the original spec assumed. Each finding below was independently reproduced against the live API, not inferred.

**It was then revised a second time (2026-07-15), and far more drastically: a full live run proved that the elaborate date-bucketed partitioning this section previously specified was not merely inefficient but actively self-defeating, and — critically — that the 10,000-item cap it existed to work around does not apply to the `$skiptoken` paging adopted in the first revision.** The workaround outlived the constraint that motivated it. The design below is consequently a large net deletion: no date buckets, no adaptive bisection, no incremental sync, no cap handling. See "The 2026-07-15 findings" and "Acquisition: a single unfiltered walk" below.

**Confirmed server constraints and bugs (do not re-litigate these without re-testing live):**

1. **`$skip` is unreliable on `$filter`-scoped queries; use the server's `<link rel="next">` `$skiptoken` continuation instead.** `$top` is not honored (the server returns its own page size regardless), and — the deeper problem, found when a real run collected only 125 rows — **`$skip` is *silently ignored* on a `Published`-date-filtered query**: `skip=0` and `skip=N` return the *same* page (with `$orderby`, deterministically identical; without, an unstable overlapping top-N). Skip-based paging therefore re-reads page 1 and any "advance `$skip` by the returned count / stop when a page has no new ids" heuristic terminates a bucket after ~2 requests. The fix is to follow OData server-driven paging: each response's feed carries `<link rel="next" href="...&$skiptoken=...">`; fetch the initial URL for a filter, then follow each response's next-link until a response has **no** next link (the definitive end-of-bucket signal). Confirmed live: following next-links walks the full result set with **zero overlap** and clean alphabetical ordering (e.g. `…AndroidStudio → ant → … → autocad → … → balabolka → bluej` across 5 pages, every entry new), and the 2023 bucket that skip-paging reported as 5 packages yielded 27+ in the first 8 next-link pages alone. This requires fetching with `Invoke-WebRequest` + `[xml]` (not `Invoke-RestMethod`, which deserializes only the entries and discards the feed-level next link). The old `-ChocoPageSize` param is gone.
2. **The hard 10,000-item cap applies to `$skip`, NOT to `$skiptoken` paging.** ~~Hard 10,000-item cap per filter context~~ — the cap is real and confirmed via the server's own error text (`$skip=10000` returns `HTTP 406`: *"Traversing more than 10000 items is no longer supported"*; `$skip=9999` still succeeds), and Chocolatey's docs describe it as specifically targeting "customers or community members who are retrieving a list of all packages, or paging through all packages". **But it is a restriction on `$skip`-based traversal only.** Confirmed live on 2026-07-15: a single `$skiptoken` next-link walk ran **282 consecutive pages to completion with zero 406s**, traversing ~11,280 underlying items — well past 10,000. Seek-based continuation does not "traverse" in the sense the server counts, which is precisely why OData offers it. **This invalidates the original spec's central premise.** Every mitigation below that exists to stay under the cap (date bucketing, adaptive bisection, per-bucket partitioning) was solving a problem that the first revision's `$skiptoken` fix had already dissolved — the two changes were tangled together and only one was ever needed.
3. **Name-based partitioning does not work, in three different ways, all silent (HTTP 200, zero results, no error):** `startswith(Id,'a')` returns nothing even at `$top=50`; ordinal range comparisons on `Id` (`Id ge 'a' and Id lt 'b'`, and even the bare single-clause `Id ge 'a'` alone) return nothing; `Id eq 'git.install'` combined with `IsLatestVersion` also returns nothing. `substringof(...)` (contains) does work, but is useless for exhaustive, non-overlapping partitioning. **Do not attempt any `Id`-based filtering for partitioning or seek-pagination** — it silently produces zero rows rather than erroring, which is far more dangerous than a loud failure.
4. **`Published`/`LastUpdated` date comparisons (`gt`/`ge`/`lt`) return correct results, but the server applies them *after* pagination — making them useless as a partitioning dimension.** They were originally adopted as "the only confirmed-working partitioning dimension" (name-based filtering being silently broken — point 3). The results are accurate; the cost model is catastrophic. Confirmed live on 2026-07-15: the server pages the underlying `IsLatestVersion` set at ~40 items/page and applies the date predicate to each page *after* selecting it, returning only the survivors. A date-scoped query therefore walks the **entire catalog** regardless of how few packages match:
   - The 2011 bucket consumed **282 pages to yield 5 rows**; nearly every page came back empty.
   - 11,202 packages ÷ 40 per page = 280.05 pages — an almost exact match for the 282 observed, confirming a full-catalog traversal per bucket.
   - The 2011 and 2012 buckets traverse the *identical* skiptoken path (`'11','capnproto'` appears at the same position in both), as does an unfiltered walk (`'11','adobeair'`) — one underlying sequence, re-walked per bucket.
   - **Partitioning by date therefore multiplies total cost by the number of buckets rather than dividing it**: ~16 years × ~280 requests ≈ 4,480 requests to collect what one unpartitioned walk collects in ~281.
   - Filtered queries are also *far* more expensive server-side: an uncached `Published`-range page took **89 seconds** (HTTP 200, `CF-Cache-Status: MISS`) versus **~300ms** for an unfiltered page. The polite-looking bucketed crawl was by far the more abusive of the two.
   - The old recency-skew analysis (sampling found 0 packages in 2013 up to 4,285 in 2026-partial, so `Published` on `IsLatestVersion` reflects when a package's *current* version shipped, not its creation date) remains accurate and is retained here as context — but it is now moot, since no bucketing survives.
5. **Sparse-bucket `$skip` weirdness** (historical note, superseded by the next-link fix in point 1): with `$skip` paging, a sparse bucket was observed re-delivering the same last entry across a range of `$skip` values before returning empty (a 3-item 2025 bucket repeated `4k-video-downloader` for `$skip` 3–9). This originally motivated a "stop when a page has no *new* package_ids" heuristic — but that heuristic is exactly what caused the 125-row full-crawl bug once overlapping pages (from ignored `$skip`, point 1) made *every* page-2 look like "no new ids". Following the server's next-link continuation instead removes the ambiguity entirely (no next link = done). A package_id dedup set is retained only as a defensive safety net, **not** as the termination signal.
6. **`Authors` (and `Id`, `LastUpdated`, `Summary`) are excluded from the OData payload's `<m:properties>` content** — the schema marks them `m:FC_KeepInContent="false"` ("feed customization": these properties are remapped onto the Atom-standard `<author>`/`<title>`/`<updated>` elements instead of appearing as `<d:Authors>` etc.). This is *why* `publisher` came back empty in earlier smoke-testing — it's not a data-quality gap, the mapper was reading the wrong element. `ConvertFrom-DFCatalogODataEntry` already has a fallback for `Id` (`$e.title`) for exactly this reason; the choco row mapper must read **`$Entry.author.name`** for publisher, not `$props.Authors` (always empty).
7. **The dedicated OData `GetUpdates` endpoint (the standard "give me changes since X" mechanism) is disabled** — Chocolatey's own docs confirm it returns `HTTP 410 Gone`. There is no built-in incremental-sync primitive. This originally forced a hand-built incremental path against the regular `Packages()` collection; as of 2026-07-15 the finding is academic, since incremental sync is gone entirely (see "Incremental sync is removed, not deferred" below).
8. **`$inlinecount=allpages` is broken** — it mirrors the requested/returned page size rather than the true total match count (confirmed: `$top=1` → `<m:count>1</m:count>`, `$top=5` → `<m:count>5</m:count>`, regardless of the filter's true match count). Do not use it to estimate totals; the only reliable way to know the catalog's size is to page through it. (The website's own listing page reports a package count — 11,202 on 2026-07-15 — which is a useful independent sanity check on a completed walk, but it is a human-readable figure on an HTML page, not an API contract; treat it as corroboration, not as a termination condition.)
9. **Responses are Cloudflare-cached** (`Cache-Control: public, max-age=1800` — 30 minutes), confirmed via `CF-Cache-Status: HIT` on repeated identical queries. A walk can therefore serve answers up to 30 minutes stale — fine for a periodic catalog snapshot, not suitable for anything needing minute-level freshness.
10. **An empty feed must be null-guarded, or it counts as one entry.** `@($xml.feed.entry)` yields `@($null)` — a one-element array containing `$null` — when a page has no entries, because PowerShell wraps the null rather than producing an empty array. This is a client-side bug, not a server behavior, and it is why the 2026-07-15 run logged empty pages as "1 entries, 0 new". Harmless there (the null mapped to `$null` and was silently dropped) but it corrupts any entry-count-based logic. The fetch seam must filter: `@($xml.feed.entry | Where-Object { $_ })`.

**Rejected alternative — scraping the website instead of the API (evaluated 2026-07-15):** `community.chocolatey.org`'s package listing pages through the full catalog without any 10,000-item ceiling, which invites the question of whether the HTML is an easier target than the "flaky" API. It is not, for a decisive reason: the listing pages carry only thin metadata (id, title, download count, description snippet), so acquiring the fields this phase needs — version, homepage, license, publisher, tags — would require one detail-page fetch **per package**: ~11,202 requests against brittle HTML, versus ~281 against a sanctioned machine interface that returns the same fields structured. That is ~40× the load on the same free service for strictly worse data. The site's freedom from the cap is also not a special feature — it is a server-rendered NuGetGallery reading its own database directly; the cap is an API-layer restriction, and (per point 2) it never applied to `$skiptoken` paging anyway. **Use the API.**

**Acquisition: a single unfiltered walk.** Issue exactly one query — `$filter=IsLatestVersion`, no date clause, no `$skip`, no `$top` — and follow the server's `<link rel="next">` `$skiptoken` continuation until a response carries no next link. That is the entire strategy. Measured live on 2026-07-15: **40 entries per page, ~300ms per request, ~281 requests for the full ~11,202-package catalog**, in clean alphabetical order (`0ad → AdobeAIR → adobedigitaleditions → …`), with no cap and no partitioning. At the jittered pacing below this is ~21 minutes of wall clock. Every package's latest version appears exactly once, so no cross-partition deduplication is needed.

Comparison with the superseded design, on identical live measurements:

| | Date-bucketed (superseded) | Single unfiltered walk |
|---|---|---|
| Requests for full catalog | ~4,480 (~16 buckets × ~280) | **~281** |
| Rows per request | ~1 (most pages empty) | **~40** |
| Server cost per request | up to **89s** uncached | **~300ms** |
| Wall clock | ~5.8h, and over the request budget | **~21 min** |
| Outcome | incomplete — dies mid-timeline, missing the recent years holding most of the catalog | complete |

**Completeness and pruning:** a walk is **complete** only if it terminated on a missing next link (not on an error, a 429, or the request budget). Prune — `DELETE FROM raw_packages WHERE source='choco' AND package_id NOT IN (<ids seen this run>)` — **only after a complete walk**; pruning on a partial walk would delete packages merely because the run stopped early. An incomplete walk still upserts everything it collected (that data is valid; it is only *unfinished*), logs an `error` describing where it stopped, and skips the prune. Because a full walk runs every time, removal detection is free — this is what the old design needed a periodic `-Fresh` reconcile pass to approximate.

**Incremental sync is removed, not deferred.** Point 4 is why: `LastUpdated gt <watermark>` is a filter, and filters are applied post-pagination, so an incremental delta would walk all ~281 pages to return a handful of changed rows — the same cost as a complete walk, for strictly less data and no removal detection. The `sync_state` table, the `last_synced_at` watermark, and the `-Fresh` switch are all deleted. (Point 7's `GetUpdates: 410 Gone` finding stands, and is now merely academic: there is no incremental mechanism, and none is wanted.)

**Flush per page, not at the end.** Rows are written to `raw_packages` as each page is parsed, not accumulated in memory and committed once the walk finishes. The 2026-07-15 run demonstrated why: it was interrupted ~430 requests deep and **lost every choco row it had collected**, because nothing was written until the end. Per-page flushing means an interrupted or failed walk leaves behind everything it had already fetched, and — combined with upsert-then-prune — costs nothing in correctness.

**Pacing and access hygiene:** delay between requests is **randomized/jittered** (e.g. uniformly sampled in a multi-second range), not a fixed interval — partly courtesy (this is a real crawl against someone else's free community service, however legitimate), partly to avoid presenting an obviously-automated fixed-cadence traffic pattern. Stay comfortably under the documented ~20 requests/minute/IP limit (a 1-hour ban follows a violation, doubling on repeat). A hard per-run request-count ceiling (`-ChocoMaxRequests`) remains as a runaway backstop: if the walk exceeds it, log an `error`, stop gracefully with whatever was collected, and skip the prune. With a complete walk now costing ~281 requests, its default drops from 2500 to **500** — enough headroom for catalog growth, tight enough to actually catch a runaway. Note that the *courtesy* argument now points the same way as the efficiency one: unfiltered pages are ~300ms of server work versus up to 89s for a filtered one, so the simpler design is also by far the gentler one.

**Row-write fault tolerance:** each row write is its own upsert (`ON CONFLICT DO UPDATE`), not a bare `INSERT` — so the sparse-bucket duplicate-redelivery bug (point 5 above) cannot abort a whole catalog's transaction by tripping the `UNIQUE(source, package_id)` constraint; a redelivered duplicate just updates the same row harmlessly. This is a correctness fix, not merely a convenience — a bare `INSERT` with no per-row isolation, combined with a confirmed-real duplicate-delivery pattern and a whole-catalog transaction with no per-row try/catch, would silently lose every row collected for the run whenever that pattern was hit. Upsert remains the right call under the single-walk design even though a clean walk delivers each package exactly once: it is what makes per-page flushing, re-runs, and interrupted-then-resumed runs all idempotent.

## Error Handling

- **Catalog-level isolation**: a total failure in one catalog (winget-pkgs download fails, choco API unreachable, no scoop buckets found) logs an `error` row and the other catalogs' acquisition still proceeds and is still written to `raw_packages`.
- **Item-level isolation**: one unparseable manifest/entry logs a `warning` row and is skipped; it never aborts the catalog's crawl.
- **Item-level isolation's cost, and the check that pays for it**: this rule converts a crash into *silent partial data*. On 2026-07-15 a single bad property read skipped 4,734 of 13,763 winget packages, and the run reported success — the only symptom was a row count nobody was comparing against anything. **Every run must therefore log both the population it found and the rows it emitted** (`found N package directories` vs `wrote M rows`; for choco, `PageCount` × ~40 vs rows) so a large gap is visible in the transcript. A `warning` count that runs to the thousands is an error condition wearing a warning's clothes: treat a systematic pattern of item-level failures as a run-level failure, not as N independent skips.
- **Row-write isolation**: writing one row's failure never aborts the rest of a catalog's batch. Choco's upsert semantics (see its Acquisition Strategy section) make this largely moot for the `UNIQUE(source, package_id)` case specifically, but any other unexpected write-time failure is still caught per-row rather than letting one bad row take down an entire catalog's transaction.
- **`review`-level entries**: logged for anything that parsed successfully but merits a later human look (see Data Model above for examples). These are not failures.
- **Choco request-budget circuit breaker**: if the walk exceeds `-ChocoMaxRequests`, it logs an `error` and stops with whatever was collected rather than continuing indefinitely — see Acquisition Strategy → Choco.
- **Choco incomplete-walk handling**: any walk that ends on anything other than a missing next link (error, 429 abort, budget exhaustion) logs an `error`, keeps every row it collected, and **skips the prune step** — see Acquisition Strategy → Choco. Never let "the run stopped early" masquerade as "these packages were removed upstream."

## Testing (Pester 5)

- Unit tests for each catalog's mapping/parsing logic (scoop manifest → row, winget locale YAML → row, choco OData entry → row) against small fixture files — pure functions, tested in isolation exactly like the existing `ConvertFrom-DFCatalogODataEntry`/`ConvertFrom-DFCatalogWingetShow` tests. The choco mapper's fixture must include an `Authors`/`Tags`/`LicenseUrl`-bearing entry shaped like the real feed (properties for `Tags`/`LicenseUrl`, but `Authors` surfaced via `entry.author.name`, not `entry.properties.Authors`) so the feed-customization gotcha has permanent regression coverage.
- No test hits real network, a real scoop install, or a real winget-pkgs download — the choco pager, the winget-pkgs zip fetch, and the scoop bucket scan each need an injectable seam (mirroring the `-FetchItems`/`-ResolveLinkage` pattern already used elsewhere in this repo) so tests supply canned data.
- **Tests that exercise strict-sensitive parsing must call `Set-StrictMode -Version Latest` themselves.** `Set-StrictMode` is dynamically scoped: the build script runs strict, but a default Pester run does not, so a mapper can pass every test and still throw in production. This is not hypothetical — it is how the 2026-07-15 winget data loss below shipped through a fully green suite.
- **The production fetch seam needs its own tests.** Because every other test injects a fake `-ChocoFetchPage`, the real network parser had *zero* coverage while being the one piece of code guaranteed to run against the live server. It is therefore factored out of the script into `ConvertFrom-DFPackageUniverseChocoFeedXml` (parsing) + `Invoke-DFPackageUniverseChocoLiveFetch` (I/O) so the parsing half is testable without a network. Required cases: a mid-walk page (entries + next-link, `http`→`https` normalized), **the last page (entries but no next link — must yield `NextUrl = $null`, not throw)**, an empty feed, and a feed with no link elements at all.
- **Fixtures must include the sparse/minimal shape, not just the rich one.** Optional fields absent is the common case in the wild, and a fixture that declares every field tests nothing about the ~34% that don't.
- A test proving the walk follows the server's next-link continuation to exhaustion: canned pages of varying, irregular sizes are all consumed without gaps or re-fetches, and the walk terminates on — and only on — a page carrying no next link.
- A test proving the query is unfiltered: assert the constructed URL passed to the injected fetch seam contains `$filter=IsLatestVersion` and **no** `Published`/`LastUpdated` clause, no `$skip`, and no `$top`. This is the regression test for the whole 2026-07-15 redesign; a date clause silently reappearing would restore the ~4,480-request behavior while still producing correct-looking data.
- A test proving duplicate-redelivery detection: a canned sequence where the same package_id reappears across several consecutive pages before a genuinely empty page must count that package once, not once per page (regression test for the confirmed sparse-bucket pagination bug). Retained as a defensive safety net even though a clean walk should never redeliver.
- A test proving choco's upsert path: seeding `raw_packages` with an existing choco row, then feeding a canned page redelivering that same `package_id` with different field values, and asserting the row is updated in place rather than erroring on the `UNIQUE(source, package_id)` constraint.
- A test proving an **empty feed yields zero entries, not one** — a canned page whose feed has no `entry` elements must contribute no rows and must not be counted as a 1-entry page (regression test for the `@($null)` null-guard bug, point 10).
- Tests proving the prune is gated on completeness: a walk ending on a missing next link prunes choco rows absent from the walk; a walk ending on an error, a 429, or budget exhaustion **keeps** every pre-existing row and prunes nothing, while logging an `error`.
- A test proving per-page flushing: a walk whose fetch seam throws on page 3 must leave pages 1–2's rows already written to `raw_packages` (regression test for the interrupted 2026-07-15 run, which lost ~430 requests' worth of collected data).
- One end-to-end test running the full Phase A script against fixtures for all three catalogs, asserting the resulting `raw_packages` table shape and row counts.
- A test confirming catalog-level failure isolation: one catalog's fetch seam throws, and the other two still populate `raw_packages` while an `error` row appears in `pipeline_log`.

## Location & Invocation

- `build/Build-DFPackageUniverseRaw.ps1` — Phase A's entry point, matching the existing `build/Build-DFCategoryDb.ps1` / `build/Build-DFToolIdentities.ps1` convention: `#Requires -Version 7.0`, full comment-based help, injectable fetch seams per catalog for testing, dot-sources `Private/*.ps1` only for what it reuses (scoop's index builder, choco's OData mapper).
- **SQLite read/write access is a second build-time-only dependency**, the `PSSQLite` module. The existing `Invoke-DFSqliteQuery` (used by the shipped module's winget provider) is read-only by construction and has no parameter binding — safe for its existing trusted, pre-escaped callers, but wrong for writing thousands of rows of untrusted scraped text (descriptions/tags routinely contain quotes/apostrophes). `PSSQLite` provides parameterized `Invoke-SqliteQuery -SqlParameters` for safe writes. Like `powershell-yaml`, this is never a dependency of the shipped DotForge module or its end users.
- Params: `-DatabasePath` (default alongside the script), `-ScoopRoot` (reuses existing default resolution), `-WingetPkgsSnapshot` (path to an already-downloaded/extracted snapshot; triggers a fresh download when omitted), `-ChocoDelayMinMs` / `-ChocoDelayMaxMs` (randomized/jittered inter-request pacing range, replacing the original single fixed `-ChocoDelayMs`), `-ChocoMaxRequests` (per-run runaway backstop on total choco request count; default 500 against a ~281-request expected walk), `-LogFile` (verbose run-transcript path; defaults to a timestamped `acquire-<UTC>.log` next to the database). **`-Fresh` is gone** — every run is a full rebuild of all three catalogs, so the flag had nothing left to mean.
- **`-WingetPkgsSnapshot` is the parameter that makes iteration bearable.** Winget's snapshot download-and-parse dominates every run (~30 minutes; ~13,700 rows), and it is entirely independent of choco. Reusing an existing snapshot while working on choco turns a 50-minute cycle into a 21-minute one. It is also what made the interrupted 2026-07-15 run survivable: scoop and winget were already written and intact when the choco walk was killed.
- **Must run strict.** The script calls `Set-StrictMode -Version Latest` at entry, and the OData mappers it reuses are written to be strict-safe. **This reverses an earlier decision (2026-07-15) and is worth understanding, because the original reasoning was backwards.** The script previously called `Set-StrictMode -Off`, on the rationale that the reused `Private/DFCatalog.*.ps1` mappers "rely on the module's non-strict runtime": choco's `Id`/`Authors` are absent from `<m:properties>` by design (feed customization — see finding #6) and resolved via fallbacks, so under strict mode those missing-property reads *throw* instead of returning `$null`. A run from a strict interactive session had produced 0 choco / 0 winget rows with `The property 'Id' cannot be found` warnings, and `-Off` was added to make that go away.

  **The strict-mode traps this actually surfaced** (all four were live data-loss bugs that non-strict would have hidden behind a green test suite, and all four are worth recognizing on sight):
  - **Dot access on an absent member throws.** `$props.Id` (XML) and `$content.Tags` (a `ConvertFrom-Yaml` Hashtable) both throw when the member is missing. Use `Get-DFXmlMember`/`Get-DFXmlText` for XML and `$hash['Key']` index access for dictionaries — both return `$null`.
  - **`$x = @(a) | Where-Object {...}` is not an array.** The `@()` wraps only `a`, so zero matches yield `$null` and one match yields a scalar; `$x.Count` then throws. Wrap the whole pipeline: `@(a | Where-Object {...})`. This one appeared **three separate times** in this phase alone.
  - **`.GetNewClosure()` rehomes a scriptblock into a fresh module scope** that can see neither script-scope functions nor `$script:` variables — so a dot-sourced function silently fails to resolve, and a `$script:` counter increments a copy nobody reads. Use a plain scriptblock when the callee needs script-scope functions, and pass mutable state as a hashtable (by reference).
  - **`@($xml.feed.entry)` is `@($null)` (Count 1) on an empty feed**, not `@()`. Filter: `@(... | Where-Object { $_ })`.

  That is precisely backwards. Strict mode was **correctly reporting a real defect** — code reading properties that do not exist — and `-Off` silenced the messenger rather than fixing the access. The cost of that trade is already recorded in this very spec: finding #6 exists *only because* non-strict mode let `$props.Authors` (always absent) silently yield `$null`, producing a plausible-looking empty `publisher` column that took live debugging to trace. Strict mode would have thrown at the exact line, immediately. The reads must therefore use explicit existence checks (`$props.Item('Id')` / `$props.PSObject.Properties['Id']`), which return `$null` for a genuinely-absent property without throwing, and let strict mode still catch *typos and wrong names* — the failure it is actually there to prevent. Note that `Set-StrictMode` is **dynamically** scoped: the script dot-sources `Private/*.ps1` into its own scope, so there is no "strict here, non-strict there" — the mappers must be strict-safe for the script to run strict at all.
- **Verbose logging (two channels).** The database's `pipeline_log` holds structured `error`/`warning`/`review` rows (queryable, survives across phases). Separately, every run writes a detailed line-oriented transcript to the `-LogFile`: per-request timing/status/entry-count, retries, budget usage, the walk's page progression and how it terminated, the prune's row count (or why it was skipped), per-catalog begin/end/row-counts, winget progress, and the winget download size/duration. Every database log entry is also mirrored to the transcript, so the file is a complete standalone post-mortem for a failed or partial run. The transcript writer never throws (a logging failure must not abort acquisition) and is designed so a diagnosis after the fact — "which request failed, with what status, after how many others" — reads straight off the file.
- **The transcript is what made the 2026-07-15 redesign possible, and this is the argument for keeping it verbose.** The entire case — the cap not applying to `$skiptoken`, filters being applied post-pagination, the 282-pages-for-5-rows cost — was reconstructed *after the fact*, from per-request log lines of a killed run, without re-touching a rate-limited API. Per-request timing and page/entry counts look like noise right up until they are the only evidence you have. Note also that they exposed the `@($null)` bug (point 10) purely as an arithmetic inconsistency: pages logging "1 entries, 0 new" against an empty dedup set is impossible, and that impossibility is what surfaced the null-guard defect.
- The working database, the verbose log files, and the downloaded winget-pkgs snapshot are **not committed** — all regenerable, and the winget-pkgs snapshot is too large for git. Default location: a new gitignored `build/.package-universe/` working directory (`universe.db`, `acquire-*.log`, `winget-pkgs/`).
- Later phase scripts (`Build-DFPackageUniverseLinks.ps1`, etc.) will open the same `universe.db` and add their own tables, each independently runnable and independently testable.
